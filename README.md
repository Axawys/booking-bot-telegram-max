# Бот онлайн-записи для Telegram и MAX

[![CI](https://github.com/Axawys/booking-bot-telegram-max/actions/workflows/ci.yml/badge.svg)](https://github.com/Axawys/booking-bot-telegram-max/actions/workflows/ci.yml)

Бот принимает записи клиентов для сервисного бизнеса: салона, мастера, студии, клиники. Клиент сам выбирает услугу, дату и время, оставляет телефон и подтверждает запись. Администратор получает заявку в Telegram, подтверждает или отклоняет её одной кнопкой и управляет расписанием прямо из чата.

Бот работает в двух мессенджерах одновременно: в Telegram и в MAX. У них общая база, общее расписание и общая логика записи, поэтому клиенты из разных мессенджеров не могут занять одно и то же время.

Проект сделан как демонстрация для портфолио. Услуги и контакты в нём условные («Услуга за 500 ₽» и т. п.), их легко заменить на настоящие.

## Возможности

### Для клиента

- Запись в несколько шагов: услуга → дата в календаре → свободное время → телефон → подтверждение.
- В календаре видны только дни, где есть свободное время; прошедшие, занятые и закрытые дни недоступны.
- Время подбирается с учётом длительности услуги: двухчасовую услугу нельзя начать за час до закрытия или поставить поверх чужой записи.
- Телефон можно отправить кнопкой из профиля мессенджера или ввести вручную. При повторной записи бот предлагает сохранённый номер.
- «Мои записи»: список предстоящих записей со статусом и отмена с подтверждением.
- Напоминания о визите за 24 и за 2 часа, с кнопкой отмены.
- Разделы «Услуги и цены» и «Контакты».
- На любом шаге можно вернуться назад или отменить оформление.

### Для администратора

Админка находится в Telegram, у администратора своё меню вместо клиентского.

- Новые заявки приходят карточкой с кнопками «Подтвердить», «Отклонить» и «Бан». Клиент сразу получает уведомление о решении.
- Если админ не ответил за 12 часов, заявка отклоняется автоматически, а время освобождается.
- Расписание на сегодня, завтра или любую дату: кто записан, телефон, услуга и сумма.
- Управление доступным временем: можно закрыть диапазон дат (отпуск), отдельный день или отдельное время (обед), а потом открыть обратно. Уже сделанные записи при этом сохраняются.
- Горизонт записи: на сколько дней вперёд клиенты видят даты (от 0 до 365).
- Статистика: записи на сегодня и неделю вперёд, визиты, отмены и отказы за 30 дней.
- Утренняя сводка в 09:00 с расписанием на день.
- Бан пользователей Telegram и MAX: все их будущие записи отклоняются, бот перестаёт им отвечать.
- Админ может переключиться в режим клиента и записаться сам, например чтобы проверить сценарий.

Команды администратора:

| Команда | Что делает |
|---|---|
| `/admin` | справка и число заявок без решения |
| `/pending` | заявки, ожидающие подтверждения |
| `/today`, `/tomorrow` | расписание на сегодня или завтра |
| `/day 05.11` | расписание на дату |
| `/stats` | статистика |
| `/schedule` | календарь доступного времени |
| `/close 05.11-10.11` | закрыть даты для записи |
| `/close 05.11 13:00-14:00` | закрыть время (можно для диапазона дат) |
| `/open 05.11-10.11` | открыть даты или время обратно |
| `/horizon 30` | открыть запись на 30 дней вперёд |
| `/ban 123 причина`, `/ban max 123` | забанить пользователя Telegram или MAX |
| `/unban 123`, `/banned` | разбанить, список забаненных |

### Защита от ошибок и спама

- Двойная запись невозможна на уровне базы данных. Каждая запись занимает слоты расписания, а на время слота стоит уникальный индекс. Если два клиента одновременно подтвердят одно время, база пропустит только первого, второй увидит «Это время только что заняли» и выберет другое. Это работает и между мессенджерами: клиент из Telegram и клиент из MAX не займут один слот.
- Закрытое администратором время тоже защищено в базе: триггер не даёт создать на него запись, даже если клиент открыл календарь до закрытия.
- Антифлуд: не больше 20 действий за 10 секунд, затем пауза.
- Лимиты: не больше 3 активных записей на клиента и 5 новых записей в сутки.
- Напоминание не уйдёт дважды: отправленные напоминания отмечаются в базе с уникальным ключом.

## Telegram и MAX

Оба бота работают с одной базой и одним набором бизнес-логики (`core/`). Различается только то, что зависит от мессенджера: кнопки, отправка сообщений, получение событий.

- **Telegram** — на aiogram 3. Здесь же админка и планировщик задач.
- **MAX** — на собственном клиенте MAX Bot API ([документация](https://dev.max.ru/docs-api)), написанном по официальной OpenAPI-схеме. Сторонние обёртки не используются.

Как мессенджеры связаны между собой:

- Заявка из MAX приходит администратору в Telegram с пометкой «MAX».
- Решение администратора, напоминания и уведомление об истечении заявки клиент получает в том мессенджере, через который записался.
- Задачи планировщика хранятся только в памяти, а источником правды остаётся база. При старте бот пересоздаёт задачи из базы, а раз в минуту сверяется с ней. Так он подхватывает записи, созданные в MAX-боте, и ничего не теряет после перезапуска.

Чем MAX отличается в реализации:

- В MAX нет обычной клавиатуры под полем ввода, поэтому главное меню сделано inline-кнопками.
- Контакт по кнопке «Отправить номер» приходит в формате vCard, номер извлекается из него.
- API MAX (`platform-api2.max.ru`) использует сертификат Минцифры (Russian Trusted Root CA), которого нет в стандартном наборе. Корневой сертификат лежит в `max_bot/certs/` и подключается только для запросов к MAX; проверка сертификатов не отключается.

## Технологии

- Python 3.13, asyncio
- aiogram 3 — Telegram Bot API
- aiohttp — клиент MAX Bot API
- SQLAlchemy 2 (async) + SQLite, миграции Alembic
- APScheduler — напоминания, истечение заявок, утренняя сводка
- pydantic-settings — настройки из `.env`
- Docker и Docker Compose
- pytest, ruff, GitHub Actions

## Развёртывание на сервере

Подойдёт любой Linux-сервер с Docker, например VPS на Ubuntu 24.04 с 1 ГБ памяти. Входящие порты открывать не нужно: оба бота сами забирают события у мессенджеров (long polling).

### 1. Установить Docker

```bash
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER   # чтобы запускать docker без sudo; затем перелогиниться
```

Проверка: `docker compose version` должен вывести версию Compose v2.

### 2. Получить токены

- **Telegram**: создайте бота у [@BotFather](https://t.me/BotFather) и скопируйте токен.
- **MAX**: на [business.max.ru](https://business.max.ru) откройте «Чат-боты» → ⋮ → «Настройки» и скопируйте токен. Если MAX не нужен, этот шаг можно пропустить: Telegram-бот работает и без него.
- **ID администратора**: свой Telegram ID можно узнать у [@userinfobot](https://t.me/userinfobot).

### 3. Скачать проект и заполнить настройки

```bash
git clone https://github.com/Axawys/booking-bot-telegram-max.git booking-bot
cd booking-bot
cp .env.example .env
nano .env
```

Минимально нужно заполнить:

```env
TELEGRAM_BOT_TOKEN=123456789:ваш-токен
MAX_BOT_TOKEN=ваш-токен-max
ADMIN_IDS=123456789
```

Остальные параметры описаны в `.env.example` и в таблице ниже.

### 4. Запустить

```bash
docker compose up -d --build
```

Compose поднимет три сервиса из одного образа:

| Сервис | Что делает |
|---|---|
| `migrate` | применяет миграции базы и завершается |
| `telegram-bot` | Telegram-бот, админка и планировщик задач |
| `max-bot` | MAX-бот |

Боты стартуют только после успешных миграций. База SQLite хранится в Docker-томе `bot-data` и переживает пересборку и перезапуск контейнеров. После перезагрузки сервера боты запускаются сами.

Если `MAX_BOT_TOKEN` не задан, сервис `max-bot` пишет об этом в лог и ждёт настройки, не мешая Telegram-боту. Когда токен появится, впишите его в `.env` и выполните `docker compose up -d`.

### 5. Проверить

```bash
docker compose ps
docker compose logs -f telegram-bot max-bot
```

В логах должно появиться `Run polling for bot @...` для Telegram и `MAX-бот ... запущен` для MAX. Затем напишите боту `/start`. Администратор увидит своё меню, клиент — клиентское.

### Обновление

```bash
git pull
docker compose up -d --build
```

Новые миграции применятся автоматически при запуске.

### Резервная копия базы

```bash
docker compose exec telegram-bot python -c "import sqlite3; sqlite3.connect('data/bot.db').backup(sqlite3.connect('data/backup.db'))"
docker compose cp telegram-bot:/app/data/backup.db ./backup-$(date +%F).db
```

Копия делается через backup API SQLite, поэтому её можно снимать на работающем боте.

## Настройки

Все параметры задаются в `.env`. Обязателен только `TELEGRAM_BOT_TOKEN`.

| Переменная | По умолчанию | Описание |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | — | токен Telegram-бота |
| `MAX_BOT_TOKEN` | пусто | токен MAX-бота; без него MAX не работает |
| `ADMIN_IDS` | пусто | Telegram ID администраторов через запятую; если пусто, записи подтверждаются автоматически |
| `TIMEZONE` | `Europe/Moscow` | часовой пояс бизнеса |
| `WORK_START`, `WORK_END` | `10:00`, `21:00` | часы работы |
| `SLOT_MINUTES` | `30` | шаг сетки расписания |
| `BOOKING_HORIZON_DAYS` | `14` | на сколько дней вперёд открыта запись (админ может изменить командой `/horizon`) |
| `BOOKING_MIN_LEAD_MINUTES` | `60` | за сколько минут до начала можно записаться |
| `REMINDER_HOURS` | `24,2` | за сколько часов напоминать о визите |
| `PENDING_TTL_HOURS` | `12` | сколько заявка ждёт решения администратора |
| `ADMIN_DIGEST_TIME` | `09:00` | время утренней сводки; пусто — без сводки |
| `RATE_LIMIT_MESSAGES`, `RATE_LIMIT_WINDOW_SECONDS`, `RATE_LIMIT_COOLDOWN_SECONDS` | `20`, `10`, `30` | антифлуд |
| `MAX_ACTIVE_BOOKINGS`, `MAX_BOOKINGS_PER_DAY` | `3`, `5` | лимиты записей на клиента |

Услуги хранятся в базе (таблица `services`): название, цена, длительность, порядок и признак активности. Тексты бота, адрес и телефон для раздела «Контакты» находятся в `core/texts.py`.

## Разработка

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
cp .env.example .env            # вписать хотя бы TELEGRAM_BOT_TOKEN
.venv/bin/alembic upgrade head
.venv/bin/python -m telegram_bot
.venv/bin/python -m max_bot
```

Тесты и проверка кода:

```bash
.venv/bin/pytest                # 73 теста, около 5 секунд
.venv/bin/ruff check . && .venv/bin/ruff format --check .
```

Тесты прогоняют сценарии через настоящий диспетчер aiogram и обработчики MAX, а запросы к мессенджерам перехватывают. Отдельно проверяются гарантии базы: гонка за слот, триггер закрытого времени, однократность напоминаний. Схема тестовой базы создаётся теми же миграциями Alembic, что и в продакшене.

Новая миграция после изменения моделей:

```bash
.venv/bin/alembic revision --autogenerate -m "описание изменения"
```

В CI (GitHub Actions) на каждый push и pull request запускаются линтер, тесты, проверка миграций (применение с нуля, сверка с моделями, откат и повторное применение) и сборка Docker-образа.

## Структура проекта

```
core/             общая логика: расписание, оформление записи, тексты, настройки
db/               модели SQLAlchemy и запросы к базе
migrations/       миграции Alembic
notifications/    уведомления в Telegram и MAX, планировщик задач
telegram_bot/     Telegram-бот: обработчики, клавиатуры, админка
max_bot/          MAX-бот: клиент API, обработчики, клавиатуры
tests/            тесты
compose.yml       сервисы migrate, telegram-bot, max-bot
```

## Ограничения

- Начатое, но не подтверждённое оформление записи хранится в памяти и сбрасывается при перезапуске бота. Сами записи хранятся в базе и не теряются.
- Один мастер или одно рабочее место: расписание общее для всех услуг.
- MAX-бот получает события через long polling. Для большой нагрузки в MAX рекомендуют webhook, для него нужен публичный HTTPS-адрес.
